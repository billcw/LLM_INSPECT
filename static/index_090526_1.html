How an LLM predicts the next token

SmolLM2-135M — 134,515,008 parameters, 30 layers, 576-dimensional vectors, 49,152-token vocabulary. Running locally on CPU.
Start here: what this model actually is

This model does exactly one thing: given some text, it produces a probability for every one of the 49,152 tokens in its vocabulary, describing how likely each is to come next.

That's the whole model. It doesn't plan a sentence. It doesn't look anything up. It computes one distribution over possible next tokens and stops. Everything else below — whole sentences, randomness, apparent creativity — is built on top of that one operation by repeating it.

Baseline to keep in mind: pure guessing would give every token 1 / 49,152 = 0.00203%. Watch how far the real numbers are from that.

1. The prompt

Tokens update as you type (tokenizer only — the model is not run). Press Enter or click Predict to run the model.
Tokens, not words — why the text gets chopped up

The model can't read letters or words. Your text is first split into tokens — chunks from a fixed vocabulary of 49,152 entries, built by an algorithm called BPE (byte-pair encoding).

Common words are usually one token; rare words get split. Most tokens include a leading space — " capital" is a different token from "capital".

So when you see " Os" or " Sh" in the predictions, the model isn't confused — it's starting to spell Osaka or Shizuoka and will finish on the next pass.

Logits, softmax, and what temperature actually changes

The model's raw output is 49,152 numbers called logits — unbounded scores, one per token. They aren't probabilities; they can be negative and don't sum to anything in particular.

Softmax turns them into probabilities: exponentiate each, divide by the total. Everything becomes positive and the set sums to 1.

Temperature divides the logits first: p = softmax(logits / T) Small T spreads them apart so softmax concentrates; large T squashes them together so it flattens. At T = 0 it collapses onto the single highest logit.

The ranking never changes. Dividing every logit by the same positive number preserves their order, so the ten tokens listed below are identical at every temperature above zero — and in the same sequence. Only the probabilities move.

Any rank from 1 to 49,152. The browser already holds the full sorted list, so this costs no forward pass. Try 5,000 and 40,000 to see how far the ranking extends.

How one token actually gets picked

The number line, and the dart

Lay all 49,152 tokens end to end on a line from 0 to 1, each occupying a segment as wide as its probability. Then throw one dart.

1. Softmax the logits → 49,152 probabilities summing to 1
2. Cumulative sum them → the segment boundaries below
3. Draw one uniform random number r in [0, 1)
4. Take the first token whose boundary exceeds r

That's the entire selection mechanism. If you imagined raffle tickets — one duplicate per unit of probability, drawn blindly from a hat — you had it essentially right. The number line is the same idea without needing to count tickets: a token at probability 0.000001 would need a million tickets, but it just gets a segment 0.000001 wide.

The dart knows nothing. The random number generator has never seen the prompt, the logits, or the tokens. It produces a number between 0 and 1 and nothing else. All the intelligence is in the segment widths — and the model computed those.

Only the top 8 segments are drawn individually; the rest are lumped into the grey block. But the arithmetic uses all 49,152 — a dart can and will land inside the grey and resolve to a specific token.

What this widget does and doesn't share with real generation

Same algorithm, different random source. This widget uses the browser's Math.random(). Actual generation in section 3 uses torch.multinomial on the server, which is why the Seed control there works and this widget has no seed.

The segments shown are exact — computed from the full 49,152-token distribution, not just the visible ones.

3. Generation — repeating the one operation

What is a "forward pass"?

A forward pass is one complete trip through the model: tokens go in at one end, 49,152 logits come out the other. "Forward" means data flows in one direction only — input to output, no loops, no going back to revise. (The backward pass only happens during training, when errors flow backward to adjust weights. That never happens here. The weights are frozen.)

Inside one forward pass, in order:

1. Each token is looked up in the embedding table, becoming a vector of 576 numbers.
2. Those vectors travel through 30 layers side by side, one vector per token position.
3. The last position's final vector is converted into 49,152 scores.

Two things follow that surprise most people. First, nothing is stored between passes — the model has no memory of previous runs. Every pass starts from scratch, and the only reason it "remembers" earlier text is that the text is fed in again as input. Second, the amount of computation is fixed. An easy prompt and a hard prompt cost exactly the same. The model can't think longer about a harder question.

Step 2 in detail: the residual stream (vectors get added to, not replaced)

A common misunderstanding: people assume the embedding assigns the vector for a token, and that's that. Or that each layer replaces it with a new one. Neither is right.

Here is what every one of the 30 layers does, in order:

h = h + attention(norm(h))
h = h + mlp(norm(h))

Look at the h + on both lines. Each sublayer computes a correction and adds it to what is already there. It does not overwrite. 30 layers × 2 sublayers = 60 additions, stacked on top of the original embedding.

This is why it's called the residual stream — the stream flows straight through from embedding to output, and layers write into it as it passes.

h_final = embedding + (60 corrections summed)

So the embedding vector is still in there at layer 30. Mathematically present, never deleted. The layers didn't replace the token's meaning; they annotated it with context.

You can verify this in section 5: the |h| column grows from about 2.5 at the embedding stage to over 700 by layer 29.

Step 3 in detail: unembedding — how 576 numbers become 49,152 scores

At the end of a forward pass you're holding 576 numbers. You need 49,152 scores. The bridge is a matrix of shape 49,152 × 576 called the unembedding matrix.

Each row of that matrix is a 576-number vector representing one vocabulary token. The multiplication is 49,152 separate dot products:

logit for " Tokyo" = dot( h_final , row_for_Tokyo )

A dot product measures alignment. The final step asks, 49,152 times: how much does the vector I've built point in the same direction as this token's vector? The best-aligned token wins.

Specific to this model: SmolLM2 has tie_word_embeddings = True, meaning the unembedding matrix is the embedding matrix — the same table used in both directions.

Read one row → token becomes a vector (start of the pass).
Dot against all rows → vector becomes token scores (end of the pass).

So the whole forward pass is: look a token up in the table, spend 30 layers adding corrections to it, then ask the same table which token the result most resembles. Section 5 shows this directly — the embeddings row reads out your last input token at nearly 100%, because that vector is that token's row.

What happens when you click Generate

The model can't write a sentence. It only predicts one token. So generation is a loop:

1. Tokenize the prompt.
2. Run one forward pass. Get 49,152 logits.
3. Pick one token (the number line above).
4. Append that token to the input.
5. Go back to step 2 with the now-longer input.

That's autoregression — the model's own output becomes part of its next input. Generating 12 tokens means 12 complete forward passes through all 30 layers. Nothing is planned ahead.

This explains a lot of failure modes. Once a wrong token is appended, it's in the context permanently. The model can't go back and fix it.

Runs and Seed — why "random" is reproducible

Runs repeats generation with identical settings. At T = 0 every run is identical. Above 0 they diverge — same distribution, different darts.

Seed fixes the pseudo-random generator's starting state. Set a seed and sample at T = 1: perfectly reproducible. Even the randomness is a deterministic algorithm producing a fixed sequence from a starting value.

Suggested sequence: T = 0, then T = 1.0, then T = 1.0 with seed 42 twice.

5. Inside one forward pass — two lenses on 30 layers

The logit lens — reading the answer out early

Normally the model converts to vocabulary scores once, at the very end. The logit lens asks: what if we did it early?

readout(h_L) = lm_head(norm(h_L))

Take the residual stream after layer 6, apply the same final normalization and the same unembedding matrix from section 3, and see what token it points at. Do that at all 31 stages and you get a trace of the prediction assembling.

Its weakness: it pretends layers L+1 through 30 don't exist.

The Jacobian lens — accounting for the layers still to come

The J-lens fixes that blind spot. Instead of pretending the remaining layers don't exist, it approximates them with a single averaged linear map:

readout(h_L) = lm_head(norm(J_L · h_L))

J_L is a 576 × 576 matrix — the average of ∂h_final / ∂h_L over a corpus. In words: if I nudge this number in the stream at layer L, how does the final vector move, on average? One matrix multiply stands in for everything layers L+1 through 30 would have done.

The cost: the unembedding matrix already exists in the weights, so the logit lens is free. The Jacobians had to be computed with automatic differentiation over a corpus and cached — about 23 minutes for 12 prompts on this machine.

Important: both lenses are approximations, and how to tell if they're lying

Logit lens: the unembedding matrix was trained to read the final layer. Applying it to layer 6 assumes the residual stream keeps a consistent reading frame throughout. Early layers producing junk may mean "the answer isn't formed yet" — or "the lens can't read this layer." Those look identical here.

Jacobian lens: a Jacobian is a linear approximation of a very non-linear computation, averaged over a corpus that may not resemble your prompt. Twelve prompts is a small corpus. And a linear map fitted to predict the final vector will tend to look prescient by design.

The one hard check: at stage 30 the Jacobian is the identity matrix, so the J-lens must reproduce the model's real output exactly. The diagnostic at the bottom reports that error. If it isn't near zero, the entire J-lens column is unreliable.

6. Attention — which tokens looked at which

How to read this grid

This is the one view in the whole tool with genuinely meaningful axes. Both are token positions from your prompt.

Rows are the token doing the looking. Columns are the token being looked at. Cell (row i, column j) is how much of position i's attention went to position j. Brighter means more.

Every row sums to 1. Each position distributes a fixed budget of attention across the positions available to it.

The grey upper triangle is the causal mask. Position 2 cannot look at position 5, because position 5 hasn't happened yet. That's not a display choice — those values are mathematically zero. It's the same constraint that lets generation cache earlier positions instead of recomputing them.

The bottom row is usually the interesting one: it's the position that produces the next-token prediction.

Why 9 heads, and what "grouped-query attention" means here

Each layer runs attention 9 times in parallel with different learned parameters. Different heads specialize — some track syntax, some follow specific words, some do things nobody has a clean name for.

This model uses grouped-query attention: 9 query heads but only 3 key/value heads, shared 3-ways. The grids below are per query head, so there are 9 of them, but the underlying keys and values are shared in groups. It's a memory optimization, not a change in what attention means.

"Mean of all heads" averages the 9 grids. Useful for a quick overview, but it smooths away exactly the specialization that makes individual heads interesting.

Two things you'll see that are easy to misread

The first column is often very bright, in many heads at once. This is a documented and widely observed pattern sometimes called an "attention sink" — the first position absorbs large amounts of attention across many heads regardless of what that token actually is. The leading explanation is that softmax forces every row to sum to 1, so a head with nothing particular to attend to has to put its budget somewhere, and the first position serves as a default. Treat a bright first column as probably not telling you something about that word's meaning.

The diagonal is often bright too — positions attending to themselves. Also usually structural rather than semantic.

The interesting signal is off-diagonal, non-first-column brightness: a later token reaching back to a specific earlier token.

Try: run this with "Japan" in your prompt, note where the last row is looking, then change Japan to France and reload. Whether the pattern visibly reroutes is something to check rather than assume — small models are noisier than the textbook pictures.
